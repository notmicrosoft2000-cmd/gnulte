Built with Go & the Linux kernel

The stack, the source layout, the tools it links to — and an honest answer about Windows.

The stack Source layout Tools we build on Portability Windows support

The stack

Standard library Go, kernel primitives, zero dependencies

go.mod is two lines long — there is nothing to vendor and nothing to audit.

Pure standard-library Go

GNULTE is written in Go using only the standard library. No third-party modules, no go.sum — every binary compiles to one static executable with the in-repo toolchain. That means a clean supply chain and trivially reproducible builds.

The kernel does the work

Shaping is a real tc netem qdisc at the interface. Spoofing and 802.11 injection are raw AF_PACKET frames. Forwarding rides iptables/sysctl. GNULTE doesn’t emulate traffic — it sets up kernel mechanics and tears them down cleanly.

Portable seams by design

Platform code lives behind build tags: inject_linux.go, arpspoof_linux.go, keys_linux.go. The *_other.go counterparts compile everywhere, so the seams for a future port already exist — but the real functionality is, and remains, the Linux path.

Self-contained distribution

install.sh builds and installs all five binaries to /usr/local/bin, bundling safety docs and the license. The OUI vendor registry ships embedded inside the binaries (internal/ident/oui.txt), so scans work fully offline.

Inside the repository

Source layout

Five commands, one shared identification engine, and small single-purpose packages. cmd/ is the public face; internal/ is where the work happens.

gnulte-go/ ├── cmd/ │ ├── gnulte/ # the MITM shaping engine (main tool) │ ├── gnulte-devices/ # LAN inventory │ ├── gnulte-scan/ # scanner + tabbed monitor │ ├── gnulte-lan/ # live LAN watch (5 screens + live map) │ └── gnulte-wifi/ # 802.11 deauth testing ├── internal/ │ ├── airframes/ # 802.11 frame crafting + raw injection │ ├── arpspoof/ # ARP spoofing (incl. stealth mode) │ ├── discover/ # LAN discovery: neighbour table + sweep │ ├── engine/ # session lifecycle: apply → monitor → restore (+ tc -s qdisc telemetry) │ ├── ident/ # OUI, mDNS, NetBIOS, OS fingerprints │ ├── inventory/ # shared device store (~/.config/gnulte-go/devices.json) │ ├── monitor/ # per-target live dashboards │ ├── netutil/ # interfaces, subnet math, sysctl/iptables helpers │ ├── out/ # colour, tables, banners │ ├── probe/ # ICMP + TCP fallback connectivity probes │ ├── reportdir/ # the ~/GNULTE Reports hub │ ├── safety/ # bundled docs + first-run acceptance record │ ├── scanner/ # parallel ping sweep (ARP sweep as root) + --watch delta engine │ ├── settings/ # config.json + settings TUI │ ├── sound/ # latency-scaled terminal beeps │ ├── traffic/ # per-target latency/jitter/loss accounting │ ├── tui/ # windows, tabs, key handling │ └── ux/ # wizard, boot checks, prompts └── install.sh / uninstall.sh

The *_linux.go / *_other.go pairs in airframes, arpspoof, monitor and tui are the portability seams mentioned above.

Tools and standards we build on

No Go libraries — but GNULTE sits on well-known Linux machinery and open standards.

GoThe language and toolchain — one static binary per tool.

The Windows question

Windows: an honest answer

GNULTE is Linux-only by design. Here is why, and what it would take to change that.

1. No netem on Windows

Shaping is applied with a kernel qdisc. Windows has no equivalent traffic-shaping API — recreating it means a WFP-based filter driver or a userspace proxy. That is a new tool, not a port.

2. No AF_PACKET

Spoofing crafts raw Ethernet + ARP frames. Windows' Npcap can send raw frames, but sustaining a MITM ARP state against the OS's own ARP cache is fragile — the Linux raw-socket path is far more reliable.

3. No monitor mode

gnulte-wifi injects 802.11 management frames. Windows does not expose monitor mode or frame injection to userspace on mainstream adapters — so the Wi-Fi tool has no Windows story at all.
Verdict: native Windows support is not planned. The core features depend on Linux kernel APIs that Windows does not provide, and papering over them would produce a different, less reliable product. GNULTE’s supported paths are native Linux (recommended), a bridged Linux VM (full functionality), or WSL2 as an evaluation sandbox — scanning, reports and CLI work; shaping, MITM and Wi-Fi do not.

What already works

Because the *_other.go stubs compile cleanly, the tree cross-compiles for Windows today — but those paths are stubs by design. WSL2 can run the real Linux binaries for discovery, scanning and reporting; nothing else does anything yet.

What would change the answer

Three things: a Windows traffic-shaping engine (WFP-based), wireless vendors exposing monitor/injection, or GNULTE growing a remote architecture — a Linux shaper driven from any OS. If any of those land, this page gets updated.

Read the practical side in the Linux / WSL2 notes and the wiki FAQ.
